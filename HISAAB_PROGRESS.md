## A. Product overview

Hisaab (`package.json` name `hisaab`) is a personal-first, local-first finance PWA. Primary use: daily expense tracking, plus income, budget cycles, recurring expenses, bills (with meter readings and attachments), assets, lending, investments, vehicles (fuel + maintenance) and an encrypted vault. No backend; all data lives in the browser.

Owner priorities, in order: (1) excellent expense tracking/reporting, (2) reliable accounts and balances, (3) complete financial overview (net worth), (4) better investment tracking, (5) data protection and backup. Phase 0 (backup) is done first because everything else changes stored data.

Typical usage today: log expenses; add investment entries (contributions + value updates). Few users.

### Expense data model (current)
`{ id, date (ISO string), amount (>0 only), categoryId, note, source: 'manual'|'recurring'|'bill', recurringId, billId, createdAt, kind? }`. `kind` is OPTIONAL and only ever `'refund'` (amount stays positive); an ordinary expense has no `kind` field (added Phase 1.2). New entries from the Expenses form store `date` as LOCAL NOON of the chosen day; older records are UTC midnight and are never rewritten.
- No `accountId`, `paymentMethod`. `amount > 0` is enforced; refunds are `kind:'refund'` with a positive amount (Phase 1.2). Settings gained one optional field, `lastCategoryId` (default `''`).
- Expenses are also created by: Bills `markPaid` (source `bill`, stored back as `bill.linkedExpenseId`), Dashboard recurring confirm (source `recurring`), `duplicateExpense`. Fuel logs and maintenance logs hold a reference to a linked expense (`findExpense`/`deleteExpense` used there).
- Income: `{ id, date, amount, sourceType, note, createdAt }`.
- Investments: fund `{ id, name, provider, notes, contributions[], valueEntries[], createdAt }`. Contributions live inside the fund, NOT in expenses, so they are already excluded from spending.

### Budget-cycle logic (`src/utils/date.js`, `useBudget.js`)
- `getCycle(date, resetDay)`: start = resetDay of this/previous month, end = (resetDay - 1) of the following month, 23:59:59.999 local. Default `cycleResetDay = 6` (settings).
- A cycle is **derived purely from the transaction date** (an expense "belongs" to the cycle containing its date; there is no stored cycle id).
- `useBudget()` computes cycle spent/remaining/category breakdown/alerts from `inCycle(cycle)` over underlying expenses (good: no summing of summaries). Budget values live in `settings.overallBudget` and `settings.categoryBudgets`.
- Dashboard and Budget use `useBudget`; Expenses page has its own cycle-only filter (see Known issues).

### Backup/export/import (current, `SettingsView.vue`)
- "Main backup" JSON (`kind: 'hisaab-main-backup'`): settings, categories, expenses, recurring, bills, income, vehicles, vehicleLogs, fuelLogs, vehicleTags, lending, meterReadings, investments.
- Separate "Vault & Assets" JSON (`kind: 'hisaab-vault-assets-backup'`): vault (still encrypted) + assets.
- CSV export of expenses (category exported as raw id, not name).
- **Not backed up:** applock record, `meta`, IndexedDB bill attachments (UI says "device-local only").
- Import: pick file via the matching button, `JSON.parse`, show a short count summary, confirm, `set()` each present key, `location.reload()`.

### D3. Phase 1.1 — pure reporting logic — implemented, unit-tested; NOT used by any screen yet
`src/utils/reporting.js` — no Vue, no storage, no imports at all. Nothing in the app imports it yet, so no user-visible behavior changed and no stored data shape changed (no migration).

- **API (all exported):**
  - Day keys / calendar math: `localDayKey` (the ONLY function that applies the local time zone), `parseDayKey`, `isDayKey`, `addDays`, `diffDays`, `daysInMonth`.
  - Periods: `resolvePeriod(id | {id:'custom',start,end}, {now, weekStartsOn})` for `this-month | last-month | this-week | last-week | this-year | previous-year | all | custom` -> `{id, startKey, endKey}` (null = unbounded).
  - Cycles: `cycleContaining(dayOrDate, resetDay)`, `currentCycle`, `previousCycle`, `adjacentCycle`, `listCycles(transactions, resetDay, now)` (cycles with data + current, newest first, with `count`/`isCurrent`), `resolveCycleFilter('all'|'current'|'previous'|{startKey,endKey})`.
  - Filtering: `resolveFilters({period, cycle, now, weekStartsOn, resetDay})` -> intersected range `{startKey,endKey,empty,period,cycle}`; `filterTransactions(list, {period, cycle, categoryId, query, now, weekStartsOn, resetDay})`.
  - Reports: `summarize(list, {range, now})` -> `{count, expenseCount, refundCount, gross, refunds, net, days, dailyAverage}`; `categoryBreakdown(list)`; `groupByDay(list)`; `compareMonths(list, {now})` -> `{currentMonth, previousMonth, daysElapsed, previousSpanDays, previousSpanClamped, monthToDate, fullMonth{currentIsComplete}, byCategory[]}`; `isRefund`.
- **Decisions / semantics:**
  - A transaction's day = its LOCAL calendar day. Both stored forms (date-picker UTC-midnight, and "now" instants) are read through `localDayKey`; stored dates are never rewritten. No `date.slice()` anywhere (a test greps the source for it).
  - Ranges are inclusive day-key ranges compared as strings, so a custom range end covers the whole end day (fixes Known issue #8's logic for the new code; the old page code is unchanged until 1.2).
  - Period and cycle are intersected (ANDed). "All cycles" = no cycle bound. Cycle membership is derived from the date. Empty intersection -> `empty: true` and no results.
  - Cycle math is pure calendar arithmetic on day keys (no `setMonth`): months shorter than the reset day start the cycle on the month's last day (reset 31: Feb 28/29, Apr 30...). Cycles are contiguous and non-overlapping. Identical to `getCycle()` in `utils/date.js` for reset days 1-28 (parity-tested over 4 years); differs for 29-31 where `getCycle` overflows.
  - Money is summed as integer cents (exact; breakdown always adds to the summary). Unreadable amount counts as 0.
  - Refund = `kind:'refund'` with a positive amount, subtracts from net. Missing/unknown `kind` = ordinary expense. **Budget (`useBudget`) NOT changed.**
  - `dailyAverage` = net / days where days = range start (or first transaction) .. min(range end, today); future days never dilute it; negative when refunds exceed spending.
  - `categoryBreakdown.share` is relative to categories with positive net, so a donut always sums to 100.
  - `compareMonths`: month-to-date vs the first N days of last month (whole of last month if it is shorter: `previousSpanClamped`); full-month compares this month so far to all of last month (`currentIsComplete`). `changePct` is `null` (not 100%) when the previous figure is <= 0.
  - Weeks start on Sunday by default (matches the existing `groupedByWeek`); `weekStartsOn: 1` for Monday.

### D5. Phase 1.3 — refund-aware Dashboard/Budget, bills linkage, local-noon forms, one CSV exporter — implemented; checked in headless Chrome; NOT checked on a real phone or with the owner's data

Owner decisions applied: (1) refunds reduce spent in Dashboard and Budget; (2) local noon for income, bill payment, fuel, maintenance forms, NOT investments; (3) `markPaid` re-creates a missing linked expense; (4) deleting a bill-payment expense marks the bill unpaid (confirmation says so), `deleteBill` keeps the expense and clears its `billId`; (5) one CSV exporter.

- **Bills model, investigated BEFORE changing (as requested):** a bill is one record per connection per billing month (`isDuplicate` blocks a second one) with a single `status` (draft/awaiting/unpaid/paid/cancelled; "overdue" is derived from unpaid + past due). Paying = `markPaid`: one full payment (amount + arrears) that creates one expense and stores `bill.linkedExpenseId`. A PAID bill CAN be paid again: the bill wizard's status dropdown lets an edited bill be set back to Unpaid (it does not touch the expense), and "Mark paid" then reappears. So "unpaid" is well defined (status `unpaid`, payment details cleared) and the earlier dangling-link bug was reachable. `deleteBill` has no confirmation and no Undo (pre-existing). I judged "unpaid" unambiguous and proceeded; the one lossy case is that a bill that was `awaiting`/`draft` before it was paid comes back as `unpaid`.

### Backup format (implemented, Phase 0)
`{ app:'hisaab', kind:'hisaab-full-backup', formatVersion:1, schemaVersion:1, exportedAt, counts:{<key>:n}, data:{ settings, categories, expenses, income, recurring, bills, meterReadings, assets, lending, investments, vehicles, vehicleLogs, fuelLogs, vehicleTags, vault }, attachments?:[{id,billId,kind,filename,mimeType,size,data:<base64>}] }`.

## K. Phase 2 design proposal: accounts, transfers, reconciliation (APPROVED with all recommended answers; all steps 2.0-2.6 implemented, see D7 and D8)

Goal: know where the money is (cash, bank, wallet, card) without changing what the budget and reports already say. The whole design is additive: if the owner never creates an account, nothing in the app changes.

### K.1 Data model

**One new storage key, `accounts`**, holding an object (like `bills` holds `{connections, bills}`):
`{ accounts: [], transfers: [], adjustments: [] }`. One key so that accounts, transfers and corrections are always backed up, restored and snapshotted together (a restore can never leave transfers pointing at missing accounts). Absent key = empty.

- **Account** `{ id, name, type: 'cash'|'bank'|'wallet'|'card'|'other', openingBalance (number, may be negative), openingDate ('YYYY-MM-DD' day key), archived (bool), notes, order, createdAt }`. `openingBalance` is the balance at the START of `openingDate`. Single currency (the app's `currencySymbol`); multi-currency is out of scope.
- **Transfer** `{ id, date (local-noon ISO), amount (> 0), fromAccountId, toAccountId, note, createdAt }`. A SEPARATE store: never an expense, never income. Both ends must be real, different accounts (money to/from outside is an expense/income). Paying a credit card = a transfer bank -> card. A transfer fee is NOT a field: record it as an ordinary expense on the source account (keeps reports honest and the model small).
- **Adjustment (reconciliation correction)** `{ id, accountId, date (local-noon ISO), amount (signed, non-zero), reconciledTo (the real balance the user entered), note, createdAt }`. A separate record type, visibly labelled "Correction", excluded from every budget/report/CSV spending figure.
- **Optional links on existing records (additive, all optional):** `expense.accountId`, `income.accountId` (a refund is an expense with `kind:'refund'`, so it carries `accountId` too and credits that account), `recurring[].accountId`. Later steps (K.8): `loan.accountId`, `repayment.accountId`; investment contributions/withdrawals in Phase 4 (proposal only).
- **Settings (optional):** `settings.defaultAccountId` (pre-selected when nothing else is known) and `settings.lastAccountId` (the last account used in a form, like `lastCategoryId`).
- **Not integrated on purpose:** the Vault's encrypted "bank accounts" (card/account NUMBERS) stay separate. The new Accounts module holds balances, not credentials.

### K.2 Records without an account ("Unassigned") and gradual migration

- A record with no `accountId`, or one pointing at an account that no longer exists, is **Unassigned**. It is never an error and never touches any balance.
- **Nothing forces the owner to migrate history.** An account's balance only counts records dated on or after its `openingDate`. The owner sets the opening balance as of a recent date (today, or the start of the cycle) and ONLY newer records need an account. Everything older is already inside the opening balance.
- For records on/after an account's opening date that have no account, the account page shows "N transactions since <date> have no account" with a one-tap review list and an optional **bulk assign** (select rows on the Expenses/Income pages, "Assign account"). Bulk assign takes a safety snapshot first and is undoable.
- Records dated BEFORE an account's opening date but assigned to it are ignored for its balance and flagged ("N records are older than this account's opening date").

### K.3 Balance rule (pure, computed from raw records, no stored running balance)

For account A with opening balance O on day D0, and an "as of" day X (default today):

`balance(A, X) = O + income(A, D0..X) + refunds(A, D0..X) - expenses(A, D0..X) + transfersIn(A, D0..X) - transfersOut(A, D0..X) + adjustments(A, D0..X)`

where each term sums records with `accountId == A` whose LOCAL day (`localDayKey`) lies in `D0..X`, all in integer cents (same as reporting). Future-dated records are excluded from the current balance and shown as "scheduled". Later extensions add movement sources (loans, investments) as extra terms, nothing else changes.
- **Pure functions** (new `src/utils/accounts.js`, no Vue/storage): `accountBalance`, `accountLedger` (chronological rows with a running balance), `unassignedSince`, `reconcileDifference`, `validateTransfer`, `totalsByType`.
- **Credit cards / negative balances:** balances are stored as "asset positive". For `card` accounts a negative balance is displayed as "Owed ₨ X" (neutral colour, not an error); a negative cash/bank balance shows a gentle "check for missing records" hint but is allowed. Net position (Phase 3) = sum of all signed balances, so a card's debt subtracts.
- **Reconciliation:** the user enters the REAL balance (and date, default today). The app shows expected balance, entered balance and the difference. If non-zero it offers "Add a correction of +/- X", which creates an Adjustment dated that day with `reconciledTo` stored. The correction appears in the ledger as "Correction" (own icon/label, never styled like spending), is excluded from budget/reports, and can be deleted with Undo. The dialog hints that big corrections usually mean missing transactions and lists the unassigned records in the period. The account also stores nothing else about reconciliation (the latest correction implies the last check).

### K.4 Invariants (each becomes a test)
1. Adding, editing or deleting accounts, transfers or adjustments never changes `computeBudget`, `summarize`, `filterTransactions`, the Dashboard, Budget or CSV spending figures (transfers and corrections are not transactions).
2. A transfer leaves the sum of all account balances unchanged.
3. Sum of balances == sum of openings + (income + refunds - expenses on assigned records dated >= each opening) + adjustments.
4. Unassigned and orphaned `accountId` records change no balance.
5. Backup export then import reproduces identical balances; an old backup imports; a restore never leaves transfers without their accounts (same key).
6. Results are identical in all four test time zones (local-day math, noon-saved dates).

### K.5 Interaction with the rest of the app
- **Budget/reporting:** unchanged (K.4.1). `filterTransactions` gains an optional `accountId` filter (all / one / Unassigned) as a plain AND; nothing else in `reporting.js` changes.
- **Bills `markPaid` and the payment modal:** a new optional account picker; default = last account used for bills, else `settings.defaultAccountId`, else none (Unassigned). The created expense carries `accountId`. Re-paying updates the account too. The bill's existing `paymentMethod` field is untouched.
- **Recurring templates:** optional `accountId` on the template; Dashboard confirm uses it, else the default account, else none.
- **Fuel / maintenance logs:** they do not create expenses today, so they do not touch balances. If the owner wants a fill-up to leave an account, they log an expense (unchanged).
- **Lending (K.8, step 2.5):** `loan.accountId` / `repayment.accountId` optional; lending out money = an outflow, a repayment = an inflow, NEITHER counted as spending or income (matching today). Proposal only until approved.
- **Investments (Phase 4, proposal only):** a contribution/withdrawal could optionally name an account as a non-spending outflow/inflow. Investment code, the D1 fix and date ordering are NOT touched now.
- **Backup format:** add `accounts` to `STORAGE_KEYS` AND `BACKUP_MODULES` with a new shape check (`{accounts[], transfers[], adjustments[]}`; unknown account ids in transfers = warning). Bump `schemaVersion` to 2 (data version) so an OLDER app refuses a newer file instead of silently dropping accounts (today it would only warn "ignoring unknown sections"). The new app keeps accepting schemaVersion 1. Importing a full v1 backup into the new app: because a full backup means "make this device match the file", the preview says "Accounts: will be cleared (this backup predates accounts)"; legacy partial files leave accounts alone and warn that replacing expenses/income may orphan `accountId`s (harmless: they become Unassigned).
- **Safety snapshot:** `buildBackup` already snapshots every `BACKUP_MODULES` key, so snapshots include accounts automatically (a test must prove it). Also take a snapshot before any BULK operation (bulk assign) and before the version stamp.
- **CSV:** the shared exporter gains an `account` column at the end (name, blank when Unassigned); one change, both exporters stay identical (existing test guards that).

### K.6 Is a data migration needed? No. Proof by field list
Everything is additive: (1) NEW key `accounts` (absent until the first account is created); (2) NEW optional `expense.accountId`; (3) NEW optional `income.accountId`; (4) NEW optional `recurring[].accountId`; (5) NEW optional `settings.defaultAccountId`, `settings.lastAccountId`; (6) later, optional `loan.accountId`, `repayment.accountId`. No field is renamed, retyped or removed; an absent `accountId` already means Unassigned, so existing data is valid as it is. The only "version" work is stamping `meta.version = 2` (for downgrade protection and the backup `schemaVersion`), which rewrites no records.
Even so, build the framework once (step 2.0) because Phases 3-4 may need a real one: `src/utils/migrations.js` with an ordered list `{from, to, up(storage)}`; before running any pending migration call `saveSnapshot('before-migration')`; each step is idempotent; the `meta.version` stamp is written LAST; on any failure restore the snapshot automatically and show an error; if `meta.version` is NEWER than the app knows, the app refuses to write and says "update the app" (downgrade protection). It runs before the composables read storage when a step rewrites existing keys (an import-order concern for `main.js`); an additive-only migration can run later. Tested with an in-memory storage, including a failing step. **Version 1 -> 2 has exactly one step: the stamp.**

### K.9 Risks
1. **Trust in balances:** a balance is only as good as the records. Mitigation: Unassigned counts, "older than opening date" flags, reconciliation corrections that are visible, never hidden as spending.
2. **Double counting with investments/loans/transfers:** mitigated by transfers being a separate store, the movement-sources design, and not wiring loans/investments until approved.
3. **Opening-date confusion** (before vs after, same day): fixed by the documented rule "start of the opening day" and tests on boundary days.
4. **Partial restores:** one key for the whole accounts store; old-backup preview wording; orphaned ids are harmless.
5. **Older app versions silently dropping accounts:** schemaVersion 2 makes them refuse the file.
6. **Dates:** all attribution via `localDayKey`; forms save local noon; old UTC-midnight records still read correctly in zones at/ahead of UTC (G17 still applies behind UTC).
7. **Scope creep into Phase 3:** the accounts total / net worth is deliberately NOT built here.
8. **Credit-card sign confusion:** one display rule ("Owed"), one storage rule (asset positive), tested.
9. **Bulk assign mistakes:** snapshot first + Undo + a confirmation with the count.
10. **Performance:** ledger and balances are linear scans over raw records (fine for thousands of rows); the ledger pages like the Expenses list.
11. **Deleting an account that is in use:** archive only, delete blocked while any record references it.

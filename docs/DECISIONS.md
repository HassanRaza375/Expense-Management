# Decisions (Nuxt migration, accounts, sync, receipts, admin)

Each entry: the decision, then why. Open choices were made by me (the brief said not to ask); change one only with a stated reason, and add a dated note under it.

## Framework and structure
- **D1. Nuxt 4 SPA (`ssr: false`), `app/` source dir.** One precached shell makes every route work offline, which is the core promise of Hisaab; SSR buys nothing for a private, signed-in ledger. Same choice as the Quran app.
- **D2. The proven pure code stays JavaScript and keeps its folder names** (`app/utils`, `app/composables`, `app/components`, `app/views`); new code is TypeScript (`app/lib/**`, `server/**`). Why: 321 tests and years of money logic depend on those files; rewriting them is risk with no benefit. Relative imports stay valid.
- **D3. Routes come from the existing route table via `pages:extend`**, not from renamed files. Why: route names, paths and titles stay identical, and `app/views` keeps its relative import depth.
- **D4. Directory auto-import scanning is turned off for `app/utils` and `app/composables`.** Generic export names (`get`, `set`, `remove`, `isRefund`...) would otherwise be registered as globals and produce duplicate-import warnings; explicit imports already exist everywhere.
- **D5. Clean URLs replace hash URLs; a startup redirect maps `/#/path` to `/path`.** Old bookmarks and the installed PWA keep working. Why a redirect and not hash mode: clean URLs are required for `/admin` and `/api` separation and for Google's OAuth callback.
- **D6. PWA through `@vite-pwa/nuxt` with the current manifest (`id: "/"`), `sw.js`, scope `/`, `registerType: "prompt"` and the existing update toast; the worker never handles `/api/`.** Same file name and scope make the new worker replace the old one on the same origin.
- **D7. Startup order is load-bearing.** `prepareData()` (migration, snapshot, auth hint) runs in a client plugin and the app is mounted only after it resolves; composables are imported dynamically afterwards, exactly as `src/main.js` does now. If the data is from a newer version or a migration fails, the app does not start (unchanged "Hisaab did not start" screen).

## Data and sync
- **D8. Guest mode is today's app, byte for byte.** Signed out, every key stays in `hisaab:*` localStorage and nothing calls the server.
- **D9. Signed in, the account is the source of truth; the device keeps a per-user offline cache and an outbox** in a new IndexedDB `hisaab-sync` (own name, version 1). Account data is never mixed with guest data. Why IndexedDB: the cache can be larger than the localStorage quota and holds base copies for merging.
- **D10. The storage wrapper (`app/utils/storage.js`) is the single place that decides where data goes.** Guest: `localStorage`. Signed in: the same API, routed to the user's cache, plus change notifications for the sync engine. Composables are unchanged.
- **D11. Document-record design on one table (`SyncDoc`)**, like the Quran app, validated by zod per collection, with indexed projection columns (`dayKey`, `amountMinor`, `kind`, `categoryId`, `accountId`, `parentId`) filled by the server. Why: one generic, well-tested sync path; the admin reads only the projection columns, so notes, receipts, vault and attachments are unreachable by construction.
- **D12. Nested arrays are flattened into their own records with a parent id** (fund contributions, withdrawals, value entries, loan repayments, goal savings, accounts/transfers/corrections, receipt metadata). Two devices adding to the same fund then never overwrite each other.
- **D13. Merge is three-way and field-level, using a stored base copy per record**; a stale push is refused by the server (`baseRevision`), the device pulls, merges, pushes again. Client clocks are never compared. A real same-field conflict is won by the device that syncs later (its local value), which converges (the other device then pulls it). Why not hash-only: field-level merge keeps both edits when two devices change different fields of the same expense.
- **D14. `theme` is device-only.** A phone in dark mode and a laptop in light mode is a normal wish; everything else in `settings` syncs. The adapter strips `theme` on push and preserves the local one on pull.
- **D15. Deletes are tombstones; pushes are idempotent** (`baseRevision` + record id; applying the same op twice gives the same result). A delete is never a row removal, so a device that was offline cannot resurrect or lose data silently. Undo of a delete re-creates the record with the same id at a newer revision.
- **D16. First sign-in never merges automatically.** The user chooses "Upload this device's data to my account" (a safety snapshot first, then Undo) or "Start with my account's data". Why: an automatic merge of two ledgers is the one way to silently double-count money.
- **D17. Time safety: the server never works out a day or month.** The client attaches the `dayKey` it already computes with `localDayKey`; the server validates `YYYY-MM-DD` as a real calendar date and groups by `left(dayKey, 7)` / `left(dayKey, 4)`. Money in projection columns is integer minor units.
- **D18. A test fails if any localStorage key is not classified `synced` or `device-only`.** App lock, meta, sidebar state, session flags and corrupt copies are device-only. The Vault is synced only as opaque ciphertext.

## Accounts, roles, privacy
- **D19. Better Auth with email + password, roles `user` and `superadmin`.** The role column has `input: false` (no request can set it); only `scripts/seed-super-admin.mjs` sets it. Rate limiting is stored in the database (serverless has no shared memory). Google sign-in, email verification and password reset are built but stay off until their keys exist; the UI says so plainly instead of failing.
- **D20. The App Lock stays a device-only screen lock** and is never synced (a screen lock that a server could reset is not a lock).
- **D21. The Vault stays encrypted in the browser with its own passphrase.** The server stores only ciphertext; the passphrase never leaves the device; the admin cannot read it. The Vault page tells the user that a lost passphrase cannot be recovered by anyone.
- **D22. The super admin is the only role that sees `/admin`; to everyone else `/admin` and `/api/admin/*` answer 404.** The admin sees amounts, dates and categories only. Every admin write goes to an audit log and a delete needs a typed confirmation; the admin cannot delete or demote themselves or the last super admin. About and Settings carry one honest line that the service owner can view account totals.

## Cloudinary and receipts
- **D23. Cloudinary is used for two things only: the profile photo and expense receipts.** Bill attachments, backups and everything else stay on the device (the Bills page says so). Uploads are signed by the server, per user, in `hisaab/<userId>/`.
- **D24. Receipts are private** (authenticated delivery; the server checks ownership and issues a short-lived signed URL; never a public URL). The existing rules stay: up to 5 per expense, shrink photos before upload, PDFs untouched, deleting an expense never deletes its files (Undo), orphans removed only by a confirmed clean-up that also deletes the remote file. Offline additions wait in an outbox and upload when online.
- **D25. Upload cap = Cloudinary's free-plan limit (10 MB for images, 100 MB for other files)** minus margin: Hisaab's own cap stays 15 MB locally but a signed-in upload is refused above 10 MB with a clear message. (Re-check the plan's limit in the Cloudinary console before launch.)

## Tooling
- **D26. Prisma pinned to exactly 7.10.1** (`prisma`, `@prisma/client`, `@prisma/adapter-pg`), like the Quran app: a bare `npm install prisma` installs a release candidate. The client is generated by `postinstall` (needs no database). Migrations are written offline with `prisma migrate diff` and applied by hand with `prisma migrate deploy`, never at runtime.
- **D27. Aiven TLS:** the project CA comes from `DATABASE_CA_CERT` (PEM) or `DATABASE_CA_FILE`; the URL's SSL parameters are stripped when a CA is set; certificate checks are never turned off.
- **D28. Secrets are read from the environment at request time, never put into `runtimeConfig` from `process.env` at build time.** `.env` is gitignored and never opened or printed by me; scripts load it with `process.loadEnvFile()`.
- **D29. Tests never reach a real service.** Playwright servers get an unreachable `DATABASE_URL` and blank keys and use a forbid-real-services helper; Vitest clears credentials. Real-service checks live only in `scripts/live/*`, run by hand against the TEST database, behind a database-name safety check.
- **D30. The e2e run is one worker, no retries, on the production build with the sync flag OFF** (the flag is baked into prerendered output; the second server flips it at request time for API tests only). Same lessons as the Quran app.

## Accounts (Phase 4)
- **D31. The test database is `defaultdb` on the owner's Aiven service, with Hisaab's tables in their own schema `hisaab_test`** (owner decision, 2026-11-20). `defaultdb` already holds a table that is not Hisaab's, so nothing outside the schema is read, changed or removed; `.env` is never edited (`scripts/live/testDb.mjs` swaps the database name and adds `?schema=` in memory). The server honours `?schema=` (`schemaOf`). The live scripts refuse any other target.
- **D32. The browser talks to Better Auth with plain `fetch`, not its client library.** Fewer bytes, no auth code in a guest build, and the Playwright tests fake the same few routes. "Who is signed in?" is `GET /api/account/session` and answers 200 with `profile: null` when signed out (a 401 would be logged as a console error on every signed-out visit).
- **D33. Roles cannot be set by a request.** `role`, `disabled` and the photo fields are `input: false`, and a database hook forces every new account to an enabled `user`. Real result against Better Auth 1.7.16: a forged `avatarPublicId` is refused (400), a forged `role`/`disabled`/`emailVerified` is ignored; `update-user` refuses all of them (400). Only `scripts/seed-super-admin.mjs` (and later the admin panel's server code) writes `role`.
- **D34. Email features (verify address, password reset) and Google sign-in are built but OFF until their keys exist.** Without a mailer, verification is not demanded (nobody could sign in) and the person is signed in after sign-up; the Account page says plainly that email is not set up and a forgotten password cannot be reset. The Google photo is never imported (`mapProfileToUser` sets the image to null). Passwords: 10 to 128 characters (the seed script wants 12).
- **D35. Profile photo = public Cloudinary delivery under `<root>/u/<userId>/avatar`** (the user id is random, so the address cannot be guessed; receipts, Phase 6, are private). The browser sends its own 512 x 512 JPEG crop (at most 512 KB); the server checks the bytes (JPEG, PNG or WebP), never the claimed type, uploads first and only then records the id. The root folder is `CLOUDINARY_FOLDER` (default `hisaab`; the live checks use `hisaab-test`).
- **D36. Deleting an account removes the database rows first** (one cascading delete: the account is gone), **then the Cloudinary files under the user's folder.** If the remote clean-up fails the account is still deleted and the failure is written to the audit log (no foreign key to the user) so the owner can remove the folder. The user must type their own email; the last enabled super admin cannot delete themself (409). The data saved on the device is never touched.
- **D37. CSRF:** the session cookie is HttpOnly and SameSite, and every state-changing route of ours also requires the request to come from this site (`Origin`, or `Sec-Fetch-Site` when there is none). Better Auth applies its own origin check to its routes.
- **D38. Rate limits are stored in the database** (a serverless host has no shared memory): sign-in 5 per minute, sign-up 10 per hour, reset and verification emails 5 per hour, per client address and path. The client address comes from `x-forwarded-for`/`x-real-ip`, which the host must set (Vercel does); without one Better Auth falls back to one shared bucket per path (docs/DEPLOY.md says so).
